# ADR 0001: Модель песочницы

- **Статус:** принято для MVP
- **Дата:** 2026-11-17
- **Контекст:** проект «Портал запроса Kubernetes-песочниц»

## Контекст

Пользователю портала нужно по одному запросу получить изолированное
Kubernetes-окружение и данные для подключения к нему через `kubectl`.

Ограничения:

- всё работает только в Docker, без внешних кластеров и облаков;
- единственный доступный Kubernetes — встроенный кластер `local` внутри
  Rancher в Docker;
- запуск должен быть воспроизводимым одной командой
  `docker compose up --build`;
- в MVP нет аутентификации пользователей портала и базы данных.

Создавать отдельный полноценный кластер (k3s, kind, k3d) на каждый запрос
внутри Docker слишком дорого по ресурсам и времени: это минуты ожидания и
сотни мегабайт на песочницу.

## Решение

Песочница в MVP — это набор объектов Rancher во встроенном кластере `local`:

1. **Проект Rancher** (`project`) — логическая граница песочницы.
2. **Namespace** (`sandbox-<id>`) внутри проекта — место для workloads
   пользователя.
3. **Отдельный локальный пользователь Rancher** (`sandbox-<id>`) — учётная
   запись с уникальным паролем.
4. **Привязка роли** `project-member` на проект — права только внутри проекта
   и его namespace.
5. **Kubeconfig** этого пользователя — выдаётся порталом вместе с endpoint и
   токеном.

Состояние песочницы хранится в метках Rancher на проекте и namespace:
`bees-in-kube/sandbox-id`, `bees-in-kube/created-at`, `bees-in-kube/owner`.
Отдельная БД в MVP не вводится.

## Почему так

- **Дёшево по ресурсам.** Namespace и RBAC создаются секундами и не требуют
  нового control plane.
- **Реальная изоляция доступа.** Отдельный пользователь и `project-member`
  не дают выйти за пределы проекта; `kubectl get namespaces` должен быть
  `Forbidden`.
- **Пользователь сразу получает рабочий kubeconfig.** Не нужно ничего
  донастраивать вручную.
- **Состояние там же, где ресурсы.** Нет рассинхронизации между БД портала и
  Rancher; `docker compose down -v` гарантированно очищает всё.
- **Достаточно для учебного MVP.** Модель можно расширять квотами, TTL и
  отдельным кластером позже.

## Последствия

### Положительные

- Быстрое создание песочницы.
- Простая очистка: удалить volume Rancher — значит удалить все песочницы.
- Минимум компонентов: не нужны БД и очередь.
- Легко тестировать: Rancher API можно замокать.

### Отрицательные и риски

- **Изоляция на уровне namespace, а не VM.** Пользовательские нагрузки делят
  один кластер `local`; шумный сосед и компрометация узла — общий риск.
- **Нет квот.** Одна песочница может занять все ресурсы кластера.
- **Нет TTL и удаления.** Песочницы живут до `docker compose down -v`.
- **Backend использует admin-токен.** Для MVP это принято, но токен даёт
  широкие права; его нельзя отдавать во фронтенд.
- **Нет аутентификации портала.** Любой, кто дошёл до портала, может создать
  песочницу.
- **Ограничение Rancher в Docker.** Требуются привилегированные контейнеры и
  6–8 ГБ ОЗУ.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
| --- | --- |
| Отдельный k3s/kind/k3d контейнер на песочницу | Тяжело по ресурсам и времени; сложнее автоматизация в Docker |
| Только namespace без отдельного пользователя | Нет отдельного kubeconfig и разграничения доступа |
| Проект + namespace без пользователя, kubeconfig admin | Пользователь получает доступ ко всему кластеру |
| Полноценный Vault/DB для состояния | Избыточно для MVP; дублирует состояние Rancher |
| Внешний managed Kubernetes | Нарушает требование «только Docker» |

## Детали реализации

- ID песочницы генерируется бэкендом (например, короткий UUID), имена
  приводятся к DNS-1123.
- Проект и namespace получают метки `bees-in-kube/*`.
- Пользователь создаётся с `mustChangePassword: false` и случайным паролем.
- Роль — `project-member`; `project-owner` и `cluster-*` не используются без
  отдельного обоснования.
- Kubeconfig генерируется от имени пользователя песочницы; endpoint
  перезаписывается на адрес, доступный с хоста.
- Ответ API содержит `id`, `namespace`, `status`, `endpoint`, `token`,
  `kubeconfig`, `created_at`.

## Безопасность

- Admin-токен Rancher хранится только на бэкенде и в `rancher-init`.
- Пароли и токены не логируются и не попадают во фронтенд.
- Пользователь песочницы не получает cluster-scoped ролей.
- Для production-сценария потребуется отдельная роль бэкенда с минимальными
  правами и аутентификация портала.

## Открытые вопросы

- Достаточно ли `project-member` для `generateKubeconfig` без cluster-роли.
- Как выдавать квоты на проект (`resourceQuota`) в следующей итерации.
- Как реализовать удаление песочницы и очистку по TTL.
- Нужен ли отдельный k3s-кластер для пользовательских нагрузок.
